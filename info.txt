Milestone 1 is implemented and working. The final checks pass: lint, production build, 49 unit tests, and 11 checks in a real headless Chromium. The initial bundle is 77 KB gzipped, and Monaco loads only when an editor opens.

What you can do now

Pick a method, type a URL and send. Params stay in sync with the URL in both directions.
Add headers, and add a JSON body in a Monaco editor.
Send, with a progress bar while waiting, and cancel in flight.
Define environments with {{variable}} substitution, using the selector and Manage dialog in the header.
See status, time and size, plus Pretty/Raw JSON, a headers table and a cookies tab. Bodies over 10 MB are download-only, and images and other binary content only get a download button for now.
Resize the sidebar and the request/response panels by dragging or with the arrow keys.
How it's built

RequestExecutionService is the interface and BrowserFetchExecutor is the implementation. Request preparation is pure, so a future backend executor can reuse it.
HTTP error statuses such as 404 show up as normal responses. Network failures, "possibly CORS", mixed content, timeout and cancel are reported as distinct errors, and the CORS case says it can't be confirmed.
The core logic is in src/app/core/ and the UI is in src/app/features/.
Bug caught by the browser test

Typing X-Token quickly into the empty header row produced -Token, because the first keystroke was lost. I rewrote the key-value editor and added a regression test. Unit tests alone wouldn't have found it.
Caveats

Browser test not in repo: the Playwright run lives in the scratchpad, not the project. The README's e2e item stays unchecked until we add Playwright as a project dependency.
Timeout: it is fixed at 30 s, with no UI option yet.
Forbidden headers: warnings appear after sending, not while editing.
Open Step 0 items: the Content Security Policy plan and the e2e tool.
Build checks: tsc and npm test don't compile templates, so always run npm run build too. I added a note about this to AGENTS.md.
Decisions to confirm

I let features/workspace import the other features, because it assembles them. This is an explicit exception in the lint config and in AGENTS.md.
Monaco is served as copied static files from /monaco/vs, not bundled. Any future CSP will need worker-src blob: for it.

What I added:

Database: schema version 3 adds environments and settings tables.
Settings and environments: theme, active environment and the rest of the app settings now survive a reload. Environments save to IndexedDB too.
Saved requests: they appear in the sidebar and open in tabs. You can save, save as, duplicate, move, rename and delete them. Selected files are never stored, only their name, size and type.
Tabs: each tab keeps its own edits, files and last response, and can send requests independently. A dot marks unsaved tabs, closing a dirty tab asks first, and a tab whose saved request is deleted becomes unsaved instead of breaking.
Storage:
A single banner shows storage load and save failures from every store.
The first-run notice says data is stored unencrypted. Acknowledging it asks the browser to keep the data. I tie that to a click because Firefox shows a permission prompt for it.
Tests: there are 53 new tests. They include migrations from v1 and v2 databases built the way the old releases built them, and persistence across a simulated reload.
Things to know:

Unsaved tabs aren't kept across a reload. They live in memory only, and the browser warns before you leave while any are dirty. I chose this over persisting them because AGENTS.md says not to store temporary UI state unnecessarily. If you want them restored, that's a small follow-up.
Environment edits show immediately and save in the background, so fast typing doesn't drop characters. A failed save shows up in the banner. The other stores save first and then update the screen.
I added src/test-setup.ts. Dexie reads indexedDB when it first loads, and the old per-spec import broke depending on which spec loaded first. It's wired in through setupFiles in angular.json and noted in AGENTS.md §17.

Milestone 4 is implemented, and all five README items are ticked. The TypeScript check, production build, lint and all 162 unit tests pass (39 new). I also drove it in Chromium against a local test API, with 34 checks passing, and nothing is committed.

What was built

JSON views:
JSON has Pretty, Tree and Raw views.
The tree opens the first two levels and shows large arrays 100 items at a time.
Invalid JSON in tree view gets an explanation.
HTML preview:
HTML opens as source, and the preview only renders when you ask for it.
It runs in an <iframe sandbox=""> with a strict content security policy inside it.
To confirm, my test page's script never ran, its external image was never requested, and the frame has no access to the app. A unit test fails if anyone loosens the sandbox.
Images and binary:
Images, including SVG, show in a preview.
Binary bodies get a download button. Download names come from Content-Disposition, then the URL, then the content type (for example big.txt).
Size limits:
Bodies above the limit are not rendered, and the viewer says so and offers a download.
The limit is 10 MB by default and can be set from 1 to 50 MB in a new Settings dialog. Bodies over 50 MB are cut off while receiving and flagged.
History:
Newest first, 100 entries by default and configurable. The oldest are deleted first.
You can open an entry in a new tab, remove one, or clear all. Cancelled and never-sent requests aren't recorded.
Authorization header values and literal credentials in the auth settings are removed. A value that is only {{placeholders}} is kept, since it holds no secret.
The values of variables marked secret are replaced by their {{name}}, so reopening still works. I read the raw IndexedDB contents in the browser test to confirm the token never reaches storage.
Things to know

Existing bug fixed: SVG was being treated as XML and never previewed, because image/svg+xml matched the +xml rule first. It now shows as an image, with a regression test.
Redaction can't catch everything:
Secrets under 4 characters aren't searched for, because replacing a 1–3 character value would mangle ordinary text.
A secret typed literally into a body field or a custom header can't be recognized. The history panel says credentials aren't kept.
Text bodies over 256 KB are stored cut short, and the entry is flagged.
HTML previews look plainer than in a browser: external images, fonts and requests are blocked, so remote images show as a broken-image icon. I chose that for safety.
XML and HTML source isn't reformatted. It's shown as received, with Monaco highlighting.
The Chromium run logged two console errors, and both come from my hostile test page being blocked. One is the script blocked by the sandbox, and the other is the external image blocked by the content security policy. They show the protections working and aren't app errors.
Limits are clamped when settings load, so a corrupt value can't leave you with a zero or enormous limit.
Database: the schema moves to version 4 with a new history table, and there's a migration test from version 3.

Milestone 5 is implemented and all four README items are ticked. The TypeScript check, production build, lint and all 232 unit tests pass, and the tests passed five times in a row. I also ran 41 checks in Chromium with real files and no console errors, and nothing is committed.

Import and Export are buttons in the header. Imports are added next to your existing data and never overwrite it. You see the format, counts and warnings before confirming, and the write is all-or-nothing.

What was built

Native JSON export/import: every request is rebuilt from known fields only. Bad entries, duplicate ids, folder cycles and cross-collection references are skipped and reported, unknown fields are dropped, and ids are regenerated.
Sensitive-data warnings:
The export dialog counts requests with credentials and secret variables before anything is written.
By default credentials are emptied and secret values become {{name}}.
Including them is a separate tick box with a plain-text warning, then a second confirmation.
I downloaded real files to check, and the default export contained no token.
Postman v2.1 import and export:
Folders, requests, bodies, Basic/Bearer/API-key auth and collection variables come across, and a collection round-trips.
Scripts are never imported or run, and unsupported parts such as GraphQL and OAuth are reported.
OpenAPI import (3.x and Swagger 2.0):
One collection, a folder per tag, and a request per operation.
An environment with baseUrl and the credential variables, which are marked secret.
Bodies are generated as examples from the schemas.
Only local #/ references are followed, and nothing is fetched.
Import safety: files over 10 MB are refused before they're read, and nesting over 64 levels is rejected. Any __proto__, constructor or prototype key is rejected, and list lengths are capped. A hostile file with __proto__ was refused in the browser test.

Things to know

YAML isn't supported. Most OpenAPI files in the wild are YAML, so this will be a common stumbling block. The error says so, but you'll need to convert to JSON first. A YAML parser would be a new dependency, so I left it for you to decide.
Postman environments aren't supported, only collections. Postman export covers one collection at a time.
Imported file fields keep only the file name, so you re-select the files before sending.
Environment values not marked secret are exported as they are, and the dialog says so.
Two bugs from earlier milestones turned up and are fixed:
Environment ordering: two environments created in the same millisecond could come back in random order. That mattered here because imports create several at once.
Collection ordering: the collection store loaded in random id order. The sidebar was unaffected because it sorts, but anything reading the store directly got an arbitrary order. I changed the load to use the sortOrder index and updated one existing test that mocked the old call.
